# ბმა „ალპიკი“ — მესაკუთრეთა თანხმობის სისტემა (v2)

ვებსისტემა, რომელშიც ამხანაგობის თითოეული მესაკუთრე შედის საკუთარი პირადი ნომრით, ხედავს მხოლოდ საკუთარ ფართებს და ელექტრონულად აწერს ხელს დოკუმენტს. მთავარი ადმინისტრატორი ხედავს და მართავს მთელ ბაზას. ინტერფეისი მუშაობს ქართულ, ინგლისურ და რუსულ ენებზე.

> დავალებაში ნახსენები „თანამშრომელი“ ამ სისტემაში არის **ამხანაგობის წევრი (მესაკუთრე)**, „ჩანაწერი/დოკუმენტი“ კი არის **ფართი** და **ხელმოსაწერი წერილების პაკეტი**.

## 2. არქიტექტურა

```
ბრაუზერი                Vercel                                        Neon (PostgreSQL)
┌──────────────┐  HTTPS ┌───────────────────────────────────────┐ TLS ┌──────────────────────┐
│ public/      │ ─────▶ │ public/  — სტატიკური ფაილები (CDN)       │     │ persons, identifiers │
│ index.html   │        │ api/index.js — ერთი სერვერული ფუნქცია    │ ──▶ │ units, unit_owners   │
│ app.js (SPA) │ ◀───── │   src/app.js     მარშრუტები და უფლებები │     │ documents            │
│ i18n.js      │  JSON  │   src/pg.js      Postgres კლიენტი       │ ◀── │ signatures (bytea)   │
│ styles.css   │        │   src/db.js      მიგრაციები             │     │ sessions, audit_log  │
└──────────────┘        │   src/seed.js    რეესტრის იმპორტი       │     │ rate_limits, meta    │
                        │   src/bootstrap.js  პირველი ადმინი      │     └──────────────────────┘
                        └───────────────────────────────────────┘
```

* **Vercel**-ზე სტატიკურ ფაილებს (`public/`) Vercel თავად ემსახურება, ხოლო ყველა `/api/*` მოთხოვნა გადადის ერთ ფუნქციაზე (`api/index.js`). ეს მითითებულია `vercel.json`-ში, სადაც უსაფრთხოების სათაურებიც არის.
* **ბაზა: PostgreSQL** (Vercel Marketplace-ის Neon). კავშირი ყოველთვის TLS-ით და SCRAM-SHA-256 ავთენტიფიკაციით მყარდება.
* **დამოკიდებულებები: არცერთი.** Postgres-თან კავშირი ხორციელდება პროექტის საკუთარი კლიენტით (`src/pg.js`), რომელიც მხოლოდ Node.js-ის ჩაშენებულ მოდულებს იყენებს. `npm install` საჭირო არ არის.
* **პირველი გაშვება:** პირველივე მოთხოვნისას ფუნქცია თავად ქმნის ცხრილებს, ტვირთავს 118 ფართს და ადმინისტრატორს ანიჭებს როლს. პარალელური გაშვებები ამას ორჯერ ვერ გააკეთებს, რადგან პროცესი Postgres-ის advisory lock-ით არის დაცული.
* **ლოკალურად ან სხვა ჰოსტინგზე** იგივე კოდი ეშვება ჩვეულებრივი სერვერით: `DATABASE_URL=... npm start`.

### ცხრილები

| ცხრილი | დანიშნულება |

| `persons` | მესაკუთრე (ფიზიკური პირი ან კომპანია): სახელი KA/EN, **role** (`member`/`superadmin`), ენა, კონტაქტი, წვდომის კოდის ჰეში, წარუმატებელი მცდელობები, დაბლოკვა |

| `meta`, `schema_version` | მიგრაციისა და იმპორტის ნიშნულები |

## 3. უსაფრთხოება

* **შესვლა:** მესაკუთრე შედის მხოლოდ პირადი ან პასპორტის ნომრით, როგორც ამხანაგობამ მოითხოვა. **მთავარ ადმინისტრატორს** ყოველთვის სჭირდება წვდომის კოდიც, რადგან ის ყველას მონაცემებს ხედავს. კოდი ბაზაში მხოლოდ **scrypt** ჰეშად ინახება.
* **გასათვალისწინებელი რისკი:** ვინც სხვის პირად ნომერს იცნობს, შეუძლია მისი სახელით შევიდეს და ხელი მოაწეროს. ყოველი შესვლა და ხელმოწერა IP-ით აღირიცხება ჟურნალში, ხოლო ადმინისტრატორს შეუძლია საეჭვო ხელმოწერის გაუქმება. თუ მეტი დაცვა დაგჭირდებათ, Vercel-ში დაამატეთ `REQUIRE_ACCESS_CODE=1`: მესაკუთრეებსაც დასჭირდებათ თქვენ მიერ გაცემული კოდი.
* **დაბლოკვა:** 5 არასწორი კოდის შემდეგ ანგარიში 15 წუთით იბლოკება (სადაც კოდი საჭიროა). IP მისამართზე მოქმედებს შეზღუდვაც, რომელიც ბაზაში ინახება და ყველა სერვერულ ფუნქციაზე ვრცელდება.
* **სესია:** შემთხვევითი 256-ბიტიანი ტოკენი, `HttpOnly`, `SameSite=Strict`, production-ში `Secure`; ბაზაში მხოლოდ ჰეშია. კოდის განახლება ან გაუქმება წევრის ყველა სესიას ხურავს.
* **CSRF:** ცვლილების ყველა მოთხოვნას სჭირდება `X-Alpiki` სათაური და იგივე Origin.
* **სათაურები:** მკაცრი Content-Security-Policy (inline სკრიპტებისა და სტილების გარეშე), `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy: no-referrer`, HSTS.
* **ხელმოწერის შემოწმება სერვერზე:** მხოლოდ ნამდვილი PNG, ზომის ლიმიტით; თანხმობა სავალდებულოა; ფართი უნდა ეკუთვნოდეს ხელმომწერს; დუბლიკატს ბლოკავს როგორც კოდი, ისე ბაზის უნიკალური ინდექსი.
* **როლი:** `superadmin` ინახება ბაზაში. მის მინიჭება შეუძლია მხოლოდ იმას, ვისაც Vercel-ის პროექტის პარამეტრებზე (`SUPERADMIN_ID`) ან უშუალოდ ბაზაზე აქვს წვდომა. ვებგვერდიდან ან API-დან როლის შეცვლის მცდელობა უარყოფილია და აღირიცხება.
* **CSV ექსპორტი** დაცულია ფორმულის ინექციისგან (Excel).

## 4. გაშვება Vercel-ზე

**წინაპირობა:** Vercel-ის პროექტი უკვე გაქვთ (`alpik-one`). კოდი იქ უნდა მოხვდეს ისევე, როგორც წინა ვერსია მოხვდა: GitHub-ის რეპოზიტორიით ან ატვირთვით.

### ნაბიჯი 1 — კოდის განახლება
1. გახსენით არქივი `alpiki-consent.zip`.
2. **GitHub-ით:** რეპოზიტორიაში წაშალეთ ძველი ფაილები და ჩადეთ ამ საქაღალდის მთელი შიგთავსი. ზედა დონეზე უნდა იყოს `api/`, `public/`, `src/`, `vercel.json`, `package.json`. შემდეგ გააკეთეთ commit/push. ### ნაბიჯი 2 — ბაზის შექმნა და დაკავშირება
1. Vercel → თქვენი პროექტი → **Storage** → **Create Database** → **Neon** (Serverless Postgres) → **Continue**.
2. აირჩიეთ რეგიონი, რომელიც ფუნქციის რეგიონთან ახლოსაა (შეცდომის ტექსტში ჩანდა `fra1`, ანუ ფრანკფურტი, ამიტომ აირჩიეთ **Frankfurt / eu-central-1**) და უფასო ტარიფი (Free).
3. **Connect Project** → აირჩიეთ `alpik-one` და მონიშნეთ **Production** (სურვილისამებრ Preview და Development) → **Connect**.
4. Vercel თავად დაამატებს `DATABASE_URL` ცვლადს. თუ დაკავშირებისას **Custom Prefix**-ს მიუთითებთ, ცვლადის სახელი შეიცვლება და სისტემა ბაზას ვერ იპოვის, ამიტომ prefix ცარიელი დატოვეთ.

### ნაბიჯი 3 — მთავარი ადმინისტრატორი

| სახელი | მნიშვნელობა |
|---|---|
| `SUPERADMIN_ID` | თავმჯდომარის პირადი ნომერი: `01020003679` |
| `SUPERADMIN_INITIAL_CODE` | თქვენ მიერ მოფიქრებული 8 სიმბოლო (ლათინური ასოები/ციფრები), მაგ. `K7PM-4XQ2` |

`SUPERADMIN_INITIAL_CODE` გამოიყენება მხოლოდ მაშინ, როცა ადმინისტრატორს ჯერ კოდი არ აქვს. პირველი შესვლის შემდეგ:
* „მესაკუთრეები“ → საკუთარი ბარათი → **„ახალი კოდის გაცემა“**. ახალ კოდს მხოლოდ სისტემა იცნობს.
* Vercel-იდან წაშალეთ `SUPERADMIN_INITIAL_CODE`.

### ნაბიჯი 4 — ხელახალი გაშვება და შემოწმება
1. **Deployments** → ბოლო ვერსია → **⋯** → **Redeploy**. ეს საჭიროა, რომ ახალი ცვლადები ამოქმედდეს.
2. გახსენით `https://alpik-one.vercel.app/api/health`. უნდა გამოჩნდეს `{"ok":true,"database":"connected"}`.
3. გახსენით `https://alpik-one.vercel.app/` და შედით თავმჯდომარის ნომრითა და `SUPERADMIN_INITIAL_CODE` კოდით.

### თუ რამე არ მუშაობს
* `/api/health` აბრუნებს `database_unavailable`: ბაზა არ არის დაკავშირებული, ან Redeploy არ გაკეთებულა. შეამოწმეთ, არის თუ არა `DATABASE_URL` სიაში Settings → Environment Variables.
* შეცდომის დეტალები ჩანს Vercel → პროექტი → **Logs**-ში.
* ადმინისტრატორი ვერ შედის: შეამოწმეთ `SUPERADMIN_ID` (სივრცეები არ აქვს მნიშვნელობა) და Redeploy.

### სარეზერვო ასლი
Neon-ში ყოველი ცვლილება ავტომატურად ინახება (point-in-time restore) ტარიფის მიხედვით განსაზღვრული პერიოდით. დამატებით, „მიმოხილვის“ გვერდიდან პერიოდულად ჩამოტვირთეთ CSV ექსპორტი.

### სამუშაო პროცესი
1. ადმინისტრატორი მესაკუთრეებს უგზავნის საიტის ბმულს.
2. მესაკუთრე შედის თავისი პირადი ნომრით, კითხულობს დოკუმენტს, მონიშნავს ფართებს და აწერს ხელს. სისტემა ადასტურებს შენახვას.
3. ადმინისტრატორი „მიმოხილვაში“ ხედავს პროგრესს ფართებით და ფართის წილით, ფილტრავს ხელმოწერილს და ხელმოუწერელს და ტვირთავს CSV-ს.
